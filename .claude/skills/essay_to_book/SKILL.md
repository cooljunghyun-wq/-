# 에세이 → 단행본 스킬 (essay_to_book)

## 이 스킬의 전제

이 스킬은 **AI가 새 글을 써주는 스킬이 아니다.** 사용자가 이미 써 둔 매주 에세이가 원재료이고, 이 스킬은 그것들을
1. 빠짐없이 모아 인벤토리로 정리하고
2. 책의 목차 구조에 맞게 배치하고
3. 오탈자·비문 교정과 장 사이 연결 문단만 최소한으로 더하고
4. 학술적 엄밀성(인용, 논지 일관성)과 최소편집 원칙 준수 여부를 검수하고
5. 자동 검증 후 Word 문서로 변환한다

**절대 하지 않는 것**: 원문의 주장을 새로 만들거나 바꾸는 것, 예시를 창작하는 것, 문장을 "더 좋게" 다시 쓰는 것, 없는 인용을 지어내는 것. 저자 본인의 학술적 저작권과 지도교수 앞에서의 정합성이 걸려 있으므로, 의미가 바뀌는 수정은 전부 사용자 승인을 받는다 (아래 "최소 편집 원칙" 참조).

## 프로젝트 구조

| 파일 | 역할 | 교체 대상 |
|------|------|-----------|
| `SKILL.md` | 프로세스, 범용 규칙 (이 파일) | 아니오 |
| `book/book-config.md` | 책 제목, 저자 정보, 목차 뼈대, 인용 스타일, 검증 규칙 | **예** (다른 책 쓸 때 이 파일만 교체) |
| `references/*.md` | 단계별 실행 문서 (아래 워크플로우에서 로드) | 아니오 |
| `scripts/verify.py` | 원고 자동 검증기 (`/publish` 단계에서 실행) | 아니오 |

## 에세이 원본 위치

`/collect` 단계가 다음 순서로 에세이 원본을 찾는다 (현재 작업 폴더 기준).

1. `essays/` 폴더
2. `원고/에세이/` 또는 `에세이/` 폴더
3. `book-config.md`의 "## 원본 위치" 섹션에 명시된 경로

셋 다 없으면 작업을 시작하지 않고 사용자에게 에세이 파일들이 어디 있는지 묻는다 (원본을 못 찾은 채 진행하면 최소편집 검수 자체가 성립하지 않기 때문이다). 지원 형식: `.md`, `.txt`, `.docx`. `.hwp`는 먼저 `.docx`나 `.txt`로 변환해 달라고 요청한다.

## 단계 별칭

아래 문서 전체에서 `/collect`, `/organize`, `/edit`, `/review`, `/publish`는 각 단계의 별칭이다. 사용자가 별칭을 말하든 "원고 정리해줘"처럼 자연어로 말하든, 해당 단계의 references 문서를 읽고 그대로 실행한다.

| 별칭 | 실행 문서 | 성격 |
|------|-----------|------|
| `/collect` | `references/collect.md` | 에세이 수집 및 인벤토리 (원본 리서치 아님) |
| `/organize` | `references/organize.md` | 목차 설계 (essay → chapter 매핑) |
| `/edit` | `references/edit.md` | 최소 편집 (원고 통합, 오탈자 교정, 연결 문단) |
| `/review` | `references/review.md` | 4인 학술 리뷰 + 최소편집 준수 검수 |
| `/publish` | `references/publish.md` | 검증 → Word 변환 → 메타데이터 |

references 문서와 `scripts/verify.py`의 경로는 **이 스킬 폴더 기준**이다. 작업 산출물(`draft/`, `output/`)은 현재 작업 폴더 기준이다.

`book/book-config.md`는 **현재 작업 폴더에서 먼저 찾고, 없으면 스킬 폴더에서 찾는다**. 두 곳 모두 없으면 작업을 시작하지 않고 사용자에게 파일 위치를 묻거나 템플릿을 채워 달라고 요청한다.

## 최소 편집 원칙 (모든 단계가 준수, 이 스킬의 핵심)

1. **오탈자·맞춤법·비문**은 고쳐도 된다 (기계적 교정)
2. **인용 형식 통일**(각주 번호, 서지 표기 방식)은 고쳐도 된다
3. **장 사이 연결 문단**(브릿지: "지난 장에서 다룬 ...은 이번 장의 ...로 이어진다")은 새로 써서 추가해도 된다. 단, 이 문단은 원문 삽입이 아니라 "연결 문단"으로 명확히 표시한다
4. **논지, 주장, 예시, 분석 내용, 문장 구조**는 사용자의 명시적 승인 없이 바꾸지 않는다. 리뷰 단계에서 이런 수정이 필요하다고 판단되면 🟡/🟢로만 표시하고, 자동 반영하지 않는다 (아래 "수정 권한 등급" 참조)
5. 모든 수정은 `edit`/`review` 단계에서 변경 로그에 **원문 vs 수정본**을 나란히 남긴다 (뒤에 지도교수나 본인이 검토할 수 있도록)

### 수정 권한 등급

| 등급 | 대상 | 처리 |
|------|------|------|
| 자동 반영 | 오탈자, 띄어쓰기, 명백한 비문, 인용 형식 불일치 | `/edit`, `/review` 단계에서 즉시 반영, 변경 로그에 기록 |
| 제안만 | 논지 보강, 근거 추가, 표현 개선, 문단 재배치 | 리뷰 파일에 🟡/🟢로 남기고 **반영하지 않음**. `/publish` 전 사용자에게 일괄 보고하고 반영 여부를 묻는다 |
| 절대 금지 | 새로운 주장·데이터·예시 창작, 없는 인용 생성 | 어떤 단계에서도 하지 않는다 |

## 작업 폴더 규칙

### 날짜 기반 프로젝트 폴더

모든 작업 산출물은 **날짜 기반 폴더** 안에 저장한다. 한 권의 책 = 하나의 날짜 폴더.

폴더 명명 규칙:
- 기본: `YYYYMMDD` (예: `20260915`)
- 같은 날 새 프로젝트를 또 시작하면 접미: `YYYYMMDD_01`, `YYYYMMDD_02`, ...
- 날짜는 `bash`의 `date +%Y%m%d`로 얻는다

폴더 구조:
```
draft/
└── 20260915/                     ← 활성 프로젝트 폴더
    ├── 01_essay-inventory.md
    ├── 02_outline.md
    ├── 03_manuscript-v1.md
    ├── 03_manuscript-v1_part1.md  ← /edit 청크 작업 중간물 (장 단위)
    ├── 03_change-log.md          ← 원문 대비 모든 수정 내역
    ├── 04_review-proofreader.md
    ├── 04_review-coherence.md
    ├── 04_review-rigor.md
    ├── 04_review-minimal-edit.md
    ├── 05_manuscript-v2.md
    └── ...

output/
└── 20260915/
    ├── final.docx
    ├── metadata.md
    ├── verify-report.md
    └── pending-suggestions.md   ← 🟡/🟢 제안 중 미반영 목록 (사용자 확인용)
```

### 활성 프로젝트 폴더 결정 로직

| 단계 | 동작 |
|------|------|
| `/collect` | 오늘 날짜의 폴더를 **새로 만든다**. 같은 이름이 이미 있으면 `_01`, `_02`로 접미를 붙인다 |
| `/organize`, `/edit`, `/review`, `/publish` | `draft/` 하위 폴더 중 **사전순 가장 최신** 폴더를 활성으로 사용한다 |

활성 폴더가 결정되면 그 경로를 사용자에게 한 줄로 알리고 작업을 시작한다:
```
활성 프로젝트 폴더: draft/20260915/
```

## 상태 마커 (Stage Completion Marker)

각 산출물 md 파일이 **완성**되었을 때, 파일 마지막에 다음 한 줄을 추가한다:

```
<!-- STAGE_COMPLETE: 01_essay-inventory -->
```

`STAGE_COMPLETE:` 뒤의 식별자는 파일명에서 `.md`를 뗀 값과 동일하다.

- 마커 있음 → 그 단계는 완료된 것으로 본다
- 마커 없음 → 부분 작성 상태로 보고 같은 파일에 이어쓰기(append)한다

부분 작성 상태에서 절대 다음 단계를 시작하지 않는다.

## 작업 흐름

5개의 핵심 단계를 순서대로 실행한다. 각 단계를 시작하기 전에 해당 references 문서를 읽고, 문서 내부의 세부 단계는 자동으로 진행한다.

| 순서 | 단계 | 내부 단계 | 최종 산출물 |
|------|------|-----------|------------|
| 1 | `/collect` | 에세이 스캔 → 메타데이터 추출 → 인벤토리 작성 | `draft/{ACTIVE}/01_essay-inventory.md` |
| 2 | `/organize` | 목차 설계 (essay → chapter 매핑, 중복/공백 식별) | `draft/{ACTIVE}/02_outline.md` |
| 3 | `/edit` | 장별 원고 통합 → 최소 편집 → 연결 문단 삽입 | `draft/{ACTIVE}/03_manuscript-v1.md`, `03_change-log.md` |
| 4 | `/review` | 4인 학술 리뷰 → 자동 반영 등급만 수정 | `draft/{ACTIVE}/04_review-*.md`, `05_manuscript-v2.md` |
| 5 | `/publish` | 검증 → Word 변환 → 메타데이터 | `output/{ACTIVE}/final.docx`, `metadata.md`, `verify-report.md` |

표지는 이 하네스에서 다루지 않는다.

### 산출물 번호 체계

| 번호 | 파일명 | 단계 |
|------|--------|------|
| 01 | `01_essay-inventory.md` | `/collect` |
| 02 | `02_outline.md` | `/organize` |
| 03 | `03_manuscript-v1.md`, `03_change-log.md` | `/edit` |
| 04 | `04_review-proofreader.md` ~ `04_review-minimal-edit.md` | `/review` |
| 05 | `05_manuscript-v2.md` | `/review` (반영 후) |

같은 번호의 파일은 덮어쓰기로 갱신한다.

## 작성 규칙 (모든 단계가 준수)

1. 저자의 원래 문체와 어미를 유지한다 (한국어 학술 논문 관행상 "-다"체가 일반적이나, `book/book-config.md`의 "저자 어미"를 우선한다)
2. 최종 산출물에는 에이전트 내부 역할명(비평가, 프루프리더 등)이 본문에 등장하지 않는다
3. 저자 표기는 `book/book-config.md`의 "저자명"으로만 한다 (학술서이므로 기본은 실명)
4. 전문 용어는 `book/book-config.md`의 "용어 통일" 목록을 따른다
5. 각 장 끝에 수평선(---)을 넣지 않는다. 장 구분은 제목(Heading)으로만 한다
6. 인용 형식은 `book/book-config.md`의 "인용 스타일"을 전체 원고에 일관되게 적용한다

## 변경 로그 표준

`03_change-log.md`와 `05_manuscript-v2.md`는 본문 첫머리에 다음 형식의 "변경 로그" 섹션을 둔다.

```markdown
## 변경 로그

| 위치 | 원문 | 수정본 | 등급 | 사유 | 반영 |
|------|------|--------|------|------|------|
| 2장 3문단 | "그러다 보니 결과가..." | "그 결과..." | 자동(비문) | 주어-술어 호응 | ✅ |
| 3장 도입 | (없음) | "1장에서 다룬 X는 3장의 Y로 이어진다" | 자동(연결문단) | 장간 연결 | ✅ |
| 4장 5문단 | "일부 연구에서는..." | (제안) 구체적 출처 보강 필요 | 제안(🟡) | 근거 보강 여지 | ❌ 사용자 확인 대기 |
```

등급이 "자동"인 항목만 ✅로 반영한다. "제안"인 항목은 반영 여부와 무관하게 이 표에 남기고, `/publish` 이전에 `output/{ACTIVE}/pending-suggestions.md`로 한 번 더 모아 사용자에게 보고한다.

## 백업 정책

다음 트리거에서만 자동 백업한다 (모든 백업은 `{ACTIVE}/_backup/`에 ISO 타임스탬프로 보관).

| 트리거 | 백업 대상 | 백업 파일명 |
|--------|-----------|-------------|
| `/review` 반영 시작 전 | `03_manuscript-v1.md` | `03_manuscript-v1_YYYYMMDD_HHMM.md` |
| `/publish` 검증 통과 시점 | `05_manuscript-v2.md` | `05_manuscript-v2_published_YYYYMMDD_HHMM.md` |

`_backup/` 폴더는 `.gitignore`에 포함된다.

## 품질 기준

- 문서 구조가 `book/book-config.md`의 목차와 완전히 일치해야 한다
- 모든 원문 에세이가 어느 장에 배치되었는지 `02_outline.md`에서 추적 가능해야 한다 (빠진 에세이가 없어야 한다)
- 인용 형식이 원고 전체에서 일관되어야 한다
- 🔴(자동 반영 대상 결함)가 0건이어야 출판 가능하다
- 🟡/🟢(제안) 항목은 미반영 상태로 출판해도 되지만, 반드시 `pending-suggestions.md`로 보고한다
- Word 문서에 `**` 마크다운 기호가 남아 있으면 안 된다
- 장별 연결 문단이 있어야 한다 (없으면 🟡)

자동 검사 가능한 항목은 `/publish` 1단계의 `scripts/verify.py`로 강제한다. 세부 규칙은 `book/book-config.md`의 "## 검증 규칙" 섹션에서 읽는다.

## 자가 채점 (최종 산출물)

`/publish` 1단계 `verify.py`는 종료 시 다음 anchor로 10점 만점 자가 채점을 출력한다.

| 점수 | 결함 상태 |
|------|-----------|
| 10점 | 🔴 0건, 🟡 0건 |
| 9점 | 🔴 0건, 🟡 1~2건 |
| 8점 | 🔴 0건, 🟡 3~5건 |
| 7점 | 🔴 1건 또는 🟡 6~10건 |
| 6점 | 🔴 2건 또는 🟡 11~15건 |
| 5점 이하 | 🔴 3건 이상 |

이 점수는 `output/{ACTIVE}/verify-report.md` 상단에 박힌다. 9점 미만이면 사용자에게 명확히 경고하고 출판을 보류할 것을 권한다. 단, 이 스킬에서 🟡는 대부분 "제안 미반영"이므로 낮은 점수 자체가 문제가 아니라 **사용자가 검토했는지 여부**가 핵심이다. verify.py 보고서는 이 점을 마지막 줄에 명시한다.
